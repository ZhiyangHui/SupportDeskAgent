# 002：结构化日志与请求 ID

## 1. 业务目标

此前 Agent 调用异常会统一返回 502，但后端没有记录原始异常，页面也无法提供可关联的诊断标识。本功能为每个 HTTP 请求建立请求 ID，并将 Agent 异常以单行 JSON 记录，使开发者可以从浏览器响应快速定位服务端日志。

## 2. 完成范围

- 接收安全的 `X-Request-ID`，缺失或非法时生成 UUID；
- 将请求 ID 写回每个 HTTP 响应头；
- 使用 ContextVar 在异步调用链中传递请求 ID；
- 输出请求完成日志，包括方法、路径、状态码和耗时；
- 输出 Agent 异常日志，包括异常类型、上游状态码和堆栈；
- 增加请求 ID 安全校验和 502 日志关联测试。

本次不引入分布式 Trace ID，不接入日志平台，也不记录请求体、客户消息或密钥。

## 3. 调用链

```text
HTTP 请求
  ↓
RequestContextMiddleware
  ├─ 校验或生成 request_id
  └─ 绑定 structlog ContextVar
        ↓
FastAPI Route
        ↓
Agent / LangGraph / DeepSeek
        ↓ 异常
agent_execution_failed JSON 日志
        ↓
FastAPI 502 响应
        ↓
Middleware 添加 X-Request-ID
        ↓
http_request_completed JSON 日志
```

## 4. 文件职责

| 文件 | 职责 |
|---|---|
| `backend/app/core/logging.py` | 日志配置、请求 ID 校验、中间件和请求访问日志 |
| `backend/app/core/config.py` | 提供可配置的日志等级 |
| `backend/app/main.py` | 在应用创建阶段装配日志和中间件 |
| `backend/app/api/routes.py` | 在 Agent 异常边界记录业务诊断字段 |
| `backend/tests/test_api.py` | 验证响应头、安全替换和日志关联 |

请求 ID 属于 HTTP 横切能力，因此由中间件统一维护，而不是让每个路由分别读取和返回。Agent 路由只补充该业务边界独有的异常字段。

## 5. 关键设计

### ContextVar

ContextVar 会随当前异步任务传播，不需要在每个函数参数中手工传递 request ID，并且并发请求之间相互隔离。中间件在请求开始时绑定、结束时清理，避免后台任务或后续请求继承错误上下文。

### 输入安全

客户端请求 ID 最长 128 个字符，只允许字母、数字、点、下划线、冒号和连字符。非法输入不会进入日志或响应头，而是被服务端 UUID 替换。

### 数据最小化

访问日志只记录方法、路径、状态码和耗时；Agent 异常日志记录异常类型、上游状态码和堆栈。不记录聊天正文、Authorization Header、API Key 或完整供应商响应体。

### 异常边界

路由已经处理的 Agent 异常由 `agent_execution_failed` 记录，中间件随后记录状态为 502 的请求完成事件。未被路由处理的异常由中间件记录为 `http_request_unhandled` 并重新抛出，不静默吞掉异常。

## 6. 使用方法

浏览器或调用方从响应头读取：

```text
X-Request-ID: 89d9dd20-2eb1-45e8-a0c5-f6dc0d9dff15
```

随后在后端输出中搜索相同值。典型错误日志包含：

```json
{
  "event": "agent_execution_failed",
  "request_id": "89d9dd20-2eb1-45e8-a0c5-f6dc0d9dff15",
  "error_type": "BadRequestError",
  "upstream_status_code": 400,
  "level": "error",
  "timestamp": "2026-08-09T00:00:00Z",
  "exception": "..."
}
```
