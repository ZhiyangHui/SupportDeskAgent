# 001：前后端聊天接口接入

## 1. 当前问题

页面点击“发送”后只有客户消息，没有 Agent 回复。根因不是 DeepSeek 或 LangGraph 无响应，而是当前 `conversationStore.sendMessage()` 只把消息写入 Pinia，从未调用后端接口。

现有链路：

```text
输入框 → Pinia 追加客户消息 → 结束
```

本功能完成后的链路：

```text
用户提交
  → Pinia 取得并清空草稿
  → 页面立即显示客户消息
  → TanStack Query Mutation 管理请求生命周期
  → Agent Service 调用 Axios
  → POST /api/v1/agent/chat
  → FastAPI 调用 LangGraph 和 DeepSeek
  → Zod 校验响应
  → Pinia 追加 Agent 回复
```

## 2. 业务目标

完成后必须满足：

1. 客户消息立即显示，不必等待模型返回；
2. 请求期间按钮显示加载状态并禁止重复发送；
3. 后端响应通过 Zod 校验后才能进入前端状态；
4. Agent 回复成功后追加到消息列表；
5. 请求失败时显示中文提示，并在不覆盖新输入的前提下恢复原草稿；
6. DeepSeek、LangSmith 等密钥始终只存在于后端。

## 3. 本次不做什么

- 不实现 SSE 流式回复；
- 不实现会话 ID 和多轮历史；
- 不把消息写入 PostgreSQL；
- 不实现自动重试和取消请求；
- 不实现登录鉴权、附件上传和消息重发按钮。

这些能力应建立在稳定的普通 HTTP 链路之上，不能为了同时实现更多功能而混淆本次排错范围。

## 4. 前置知识

- `Pinia` 管理浏览器中的共享会话状态；
- `TanStack Query Mutation` 管理一次写请求的加载、成功和失败状态；
- `Axios` 负责 HTTP 通信；
- `Zod` 在运行时检查后端响应，补足 TypeScript 只在编译期生效的限制；
- Vue `Composable` 用于组合 Service、Mutation 和 Store，不渲染页面。

## 5. 文件职责与设计取舍

| 文件 | 只负责什么 | 不应该负责什么 |
|---|---|---|
| `frontend/.env.example` | 声明可公开的后端地址 | 保存任何密钥 |
| `src/types/agent.ts` | Agent API 的运行时 Schema 和静态类型 | 发请求、修改状态 |
| `src/lib/http.ts` | Axios 基础地址、超时和公共协议配置 | 知道具体业务接口 |
| `src/services/agent-service.ts` | Agent 接口路径、请求体和响应校验 | 操作 Pinia 或页面 |
| `src/stores/conversation.ts` | 草稿和消息列表等客户端状态 | 发网络请求、维护请求状态 |
| `src/composables/useAgentChat.ts` | 协调 Mutation、Service 与 Store | 编写页面 HTML |
| `SupportWorkspace.vue` | 展示状态并接收用户操作 | 拼接 URL、解析响应 |
| `src/styles/main.css` | 错误提示等视觉规则 | 保存业务状态 |

这样拆分的关键原因是：Pinia 与 TanStack Query 管理的不是同一类状态。消息列表是客户端当前要展示的会话状态；请求是否进行、是否失败则是服务端交互状态。把二者全部塞进 Store 会产生重复状态和同步问题。

## 第二步：定义 Agent API 数据契约

### 新建 `frontend/src/types/agent.ts`

该文件先写，因为 Service 需要依赖这里的 Schema 和返回类型。

```ts
import { z } from "zod";

// 这些枚举值来自后端 Pydantic 模型。集中定义后，接口字段变化时只需要修改一处。
export const supportIntentSchema = z.enum([
  "general",
  "account",
  "order",
  "ticket",
  "complaint",
]);

export const ticketPrioritySchema = z.enum(["low", "medium", "high", "urgent"]);

// TypeScript 无法约束运行时网络数据，因此响应进入应用前必须经过 Zod 校验。
export const agentChatResponseSchema = z.object({
  reply: z.string().min(1),
  intent: supportIntentSchema,
  priority: ticketPrioritySchema,
  requires_human: z.boolean(),
  reason: z.string().min(1),
});

export type AgentChatResponse = z.infer<typeof agentChatResponseSchema>;
```

### 关键理解

`response.data as AgentChatResponse` 只是告诉 TypeScript“相信我”，并没有检查真实数据。`agentChatResponseSchema.parse()` 才会在运行时拒绝缺少字段或枚举错误的响应。

## 第四步：封装 Agent Service

### 新建 `frontend/src/services/agent-service.ts`

Service 是前端唯一知道后端路径、请求体字段和响应 Schema 的业务边界。

```ts
import { httpClient } from "@/lib/http";
import { agentChatResponseSchema, type AgentChatResponse } from "@/types/agent";

/** 调用客服 Agent，并在外部数据进入业务状态前完成运行时校验。 */
export async function sendAgentMessage(message: string): Promise<AgentChatResponse> {
  // 请求字段必须与后端 ChatRequest 保持一致，Service 是前端唯一了解该协议的位置。
  const response = await httpClient.post<unknown>("/api/v1/agent/chat", { message });
  return agentChatResponseSchema.parse(response.data);
}
```

`post<unknown>` 是刻意设计：网络响应在验证前就是未知数据，不能提前把它假设成可信的 `AgentChatResponse`。

## 第五步：重构 Pinia 会话状态

### 完整替换 `frontend/src/stores/conversation.ts`

Store 不再提供会混合网络职责的 `sendMessage()`。它只提供取得草稿、恢复草稿和追加不同角色消息的动作。

```ts
// 会话 Store 只维护跨组件共享的客户端状态，服务端会话历史将交给 TanStack Query 缓存。
import { defineStore } from "pinia";
import { computed, ref } from "vue";

import type { SupportMessage } from "@/types/support";

// 演示消息暂时保留在前端，接入会话查询接口后再由服务端数据替换。
const initialMessages: SupportMessage[] = [
  {
    id: "message-1",
    role: "agent",
    content: "您好，我是 SupportDesk 智能客服。请告诉我您遇到的问题，我会优先从企业知识库中查找答案。",
    time: "09:42",
  },
  {
    id: "message-2",
    role: "customer",
    content: "我的企业版账号今天突然无法登录，重置密码后仍然提示账号异常。",
    time: "09:43",
  },
  {
    id: "message-3",
    role: "agent",
    content: "我已识别到这是账号访问问题。为保护企业数据，我会先核对账号状态；如果检测到安全风险，将自动转交人工客服处理。",
    time: "09:43",
  },
];

export const useConversationStore = defineStore("conversation", () => {
  // messages 会同时被消息列表和未来的会话摘要消费，因此放入 Pinia，而不是页面局部状态。
  const messages = ref<SupportMessage[]>(initialMessages);
  const draft = ref("");

  // 发送条件集中计算，快捷问题和文本输入就不会分别维护一套校验规则。
  const canSend = computed(() => draft.value.trim().length > 0);

  function setDraft(content: string): void {
    // 快捷问题与输入框共用同一份草稿，避免两个入口出现内容不同步。
    draft.value = content;
  }

  function takeDraft(): string | null {
    // 返回标准化后的快照，避免请求期间输入框变化影响已经发出的消息。
    const content = draft.value.trim();
    if (!content) return null;

    draft.value = "";
    return content;
  }

  function restoreDraft(content: string): void {
    // 用户可能已开始输入下一条消息，因此失败恢复不能覆盖非空草稿。
    if (!draft.value.trim()) draft.value = content;
  }

  function appendMessage(role: SupportMessage["role"], content: string): void {
    const normalizedContent = content.trim();
    if (!normalizedContent) return;

    messages.value.push({
      id: crypto.randomUUID(),
      role,
      content: normalizedContent,
      time: new Intl.DateTimeFormat("zh-CN", {
        hour: "2-digit",
        minute: "2-digit",
        hour12: false,
      }).format(new Date()),
    });
  }

  function appendCustomerMessage(content: string): void {
    appendMessage("customer", content);
  }

  function appendAgentMessage(content: string): void {
    appendMessage("agent", content);
  }

  return {
    messages,
    draft,
    canSend,
    setDraft,
    takeDraft,
    restoreDraft,
    appendCustomerMessage,
    appendAgentMessage,
  };
});
```

### 为什么提取 `appendMessage`

客户消息和 Agent 消息的 ID、时间与内容标准化规则完全相同，只有角色不同。提取内部函数可以防止两种消息以后出现不同的时间格式或校验规则，但该函数不对 Store 外部暴露，避免调用者传入任意角色。

## 第六步：编写聊天 Composable

### 新建 `frontend/src/composables/useAgentChat.ts`

这个文件是完整调用链的编排层。它允许 Service、Pinia 和 TanStack Query 保持各自独立。

```ts
import { useMutation } from "@tanstack/vue-query";

import { sendAgentMessage } from "@/services/agent-service";
import { useConversationStore } from "@/stores/conversation";

/** 连接网络请求与会话状态，让页面只关心提交、加载和错误反馈。 */
export function useAgentChat() {
  const conversationStore = useConversationStore();

  const mutation = useMutation({
    mutationFn: sendAgentMessage,
    onSuccess(response) {
      // Service 已校验响应，这里只把可展示内容同步到客户端会话状态。
      conversationStore.appendAgentMessage(response.reply);
    },
    onError(_error, submittedContent) {
      // 请求失败时保留已显示的客户消息；仅在输入框为空时恢复原文，避免覆盖用户新输入。
      conversationStore.restoreDraft(submittedContent);
    },
  });

  function submitDraft(): void {
    // 一次只允许一个模型请求，避免双击造成重复消息、重复工具调用和额外模型费用。
    if (mutation.isPending.value) return;

    const content = conversationStore.takeDraft();
    if (!content) return;

    // 客户消息先本地展示，Agent 回复稍后由 Mutation 成功回调追加。
    conversationStore.appendCustomerMessage(content);
    mutation.mutate(content);
  }

  return {
    submitDraft,
    isPending: mutation.isPending,
    error: mutation.error,
  };
}
```

### 失败恢复为什么判断草稿是否为空

模型请求可能持续数秒，用户在等待期间可能已经输入下一条消息。如果失败回调无条件恢复旧问题，就会覆盖新输入，造成不可恢复的数据丢失。因此 `restoreDraft()` 只在当前草稿为空时恢复。

## 8. 错误排查

| 现象 | 优先检查 |
|---|---|
| 页面没有变化 | 表单是否绑定 `submitDraft`，浏览器控制台是否报错 |
| 没有网络请求 | `useAgentChat()` 是否在组件顶层调用 |
| 请求地址错误 | `frontend/.env.local` 与 Vite 是否重启 |
| CORS 错误 | 后端是否允许 `http://localhost:3000` |
| HTTP 422 | 请求体是否为 `{ "message": "内容" }` |
| HTTP 503 | `backend/.env` 是否配置 DeepSeek Key |
| HTTP 502 | 查看后端终端中的模型供应商错误 |
| HTTP 200 但无回复 | 查看 Zod 是否因响应结构不一致而报错 |
| 请求超时 | 检查模型服务、余额、限流和网络状态 |

前端只展示统一中文错误，但开发者仍可以在浏览器 Console 和 Network 面板查看技术细节。不要直接把 Axios 原始错误渲染给最终用户。

## 11. 安全与长期约束

- DeepSeek 与 LangSmith 密钥只能保存在 `backend/.env`；
- 浏览器只访问 FastAPI，不能直接访问模型供应商；
- 外部响应必须通过 Zod 后才能进入 Pinia；

- 页面不展示供应商原始异常、内部堆栈或敏感配置；
- Pinia、TanStack Query、Service 的职责不能因为功能简单而合并。
