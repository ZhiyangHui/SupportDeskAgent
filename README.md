# SupportDeskAgent

一个面向企业售后场景的 AI 客服与工单系统。

客户可以直接用自然语言咨询问题、查询订单、创建和跟进工单；企业客服则在工作台处理工单、维护知识库，并在需要时接管对话。

项目的重点不是让 AI “聊得像客服”，而是让它在明确的流程和权限范围内，**查到信息、补齐问题、调用工具完成操作，并留下可核对的记录**。

> 项目仍在持续开发，当前用于学习、演示和功能验证。订单为模拟数据，不连接真实交易平台，不执行退款、转账或支付。

## 一个典型使用场景

客户说：

> 我的键盘有问题，想申请维修，帮我建个工单。

系统会根据对话进入对应流程，查询该客户在当前企业的订单；需要时请客户选择订单、补充售后诉求，再通过工具登记工单。客户之后可以继续说“帮我查一下进度”或“修改一下问题描述”。

如果需要人工处理，客户可以申请转人工。企业客服在工作台看到待接管会话后，直接接管并回复，不需要客户重新描述一遍问题。

## 现在可以做什么

### 对客户：在一个对话里处理售后问题

- **选择企业咨询**：客户登录后选择要联系的企业，不同企业的业务记录相互隔离。
- **查询和创建模拟订单**：用于演示订单售后流程，不依赖外部电商平台。
- **用自然语言创建工单**：根据订单和问题登记售后诉求，缺少必要信息时继续询问。
- **查询、跟进和修改工单**：查看自己的处理记录；修改前展示预览，确认后才提交。
- **查询企业知识库**：根据已发布资料回答售后规则等问题，并提供来源。
- **申请人工客服**：在原会话中继续沟通，不必换一个聊天入口。

### 对企业客服：集中处理客户问题

- **客户与会话工作台**：查看本企业客户的会话，发现并接管待处理的人工请求。
- **工单管理**：查看问题详情、处理状态和修改记录。
- **知识库管理**：录入文本或上传 TXT / Markdown，查看原文和切分片段，确认发布或停用资料。
- **历史经验整理**：从已解决或已关闭工单中选择素材，补充解决办法、审核脱敏后发布为经验。
- **Agent 运行记录**：查看执行步骤、工具调用及错误信息，方便排查“为什么没有完成”。
- **领域知识浏览**：查看通用排查路径、处理办法和适用条件，不需要在前端逐条填写图谱。

客户与企业员工使用独立账号及登录会话。客户只能访问自己的业务记录，员工只能处理所属企业的业务数据。

## AI 是怎样工作的

项目使用 LangChain 连接模型和工具，使用 LangGraph 组织多轮处理流程。模型负责理解表达、整理信息；程序负责权限、状态、确认和实际业务操作。

以修改工单为例：

```text
客户说“帮我修改工单”
          ↓
查询可访问的工单，请客户选择
          ↓
展示可修改内容，收集修改要求
          ↓
展示修改前后的预览
          ↓
客户确认后调用工具，保存结果和修改记录
```

这不是让模型随意操作数据库。订单查询、建单和修改等能力通过指定工具执行，服务端仍会检查身份、业务范围和数据版本。

### 多轮对话与排错

- 对话消息和流程状态持久化保存，正常结束的多轮对话可以继续，不只存在浏览器里。
- 模型输入会进行长度裁剪，不等于删除数据库中的聊天历史。
- 长期记忆目前保存客户显式设置的回复偏好，不自动收集所有个人信息。
- 请求带有请求 ID，结合结构化日志和运行记录定位问题；可选接入 LangSmith 查看调用链。
- 关键业务写入有重复请求保护。结果不确定时提示核对，不把“模型说完成了”当作实际成功。

## 知识库与知识图谱有什么区别

| 部分 | 主要回答的问题 | 当前状态 |
| --- | --- | --- |
| 企业知识库（RAG） | “这家企业的售后规则怎么说？依据是哪段资料？” | 已接入客服问答 |
| 售后领域知识图谱（Neo4j） | “这类现象有哪些可能原因，应该怎样核实和处理？” | 已完成存储、版本发布和只读浏览，尚未接入 Agent |

**RAG** 可以理解为“先查资料，再回答”：后端从当前企业已发布的知识中检索相关片段，再让模型结合资料回答。没有可靠依据时，不应自行编造规则。

**领域知识图谱**保存长期可复用的解法，不复制客户、订单、工单或知识文档全文。结构固定为产品类别、问题现象、可能原因、核实步骤、处理方案和条件，并用完整路径将它们组织起来，避免拼错不同解法。

目前图谱包含 15 个领域概念和 2 条演示排查路径，由后端版本化知识包维护，启用后自动加载。示例未经具体厂商认证，不代表正式售后政策，也不会自动诊断或承诺免费维修。

## 技术栈

| 层次 | 使用的技术 | 在项目中的作用 |
| --- | --- | --- |
| 前端 | Vue 3、TypeScript、Vite、Element Plus | 客户入口与企业工作台 |
| 前端状态与请求 | Pinia、Vue Router、TanStack Query | 页面路由、交互状态和服务端数据管理 |
| 后端 | Python、FastAPI、Pydantic | 提供接口、校验数据、组织业务处理 |
| Agent | LangChain、LangGraph、DeepSeek | 理解问题、编排流程、调用业务工具 |
| 数据与检索 | PostgreSQL、pgvector、SQLAlchemy、Alembic | 业务数据、向量检索及数据库迁移 |
| 领域知识 | Neo4j | 存储有条件的售后排查路径 |
| 记忆与追踪 | PostgreSQL Checkpointer / Store、LangSmith、structlog | 多轮状态、回复偏好和排错 |
| 开发验证 | Docker Compose、pytest、Ruff、mypy、Playwright | 本地运行、代码检查和自动化测试 |

Embedding（文本向量化）服务与聊天模型分开配置。依赖清单中的预留库不代表对应功能已全部实现。

## 本地运行

以下步骤在项目根目录执行。需要准备 Python 3.12、与前端依赖兼容的 Node.js / pnpm，以及 Docker Desktop 或 Docker Engine + Compose。当前一键脚本主要面向本地开发，在 macOS 上可自动打开 Docker Desktop。

### 1. 安装依赖

```bash
# 创建项目虚拟环境，并安装后端依赖。
python3.12 -m venv .venv
./.venv/bin/python -m pip install -r requirements.txt

# 前端依赖独立安装，不放进 Python 虚拟环境。
(cd frontend && pnpm install)
```

### 2. 准备配置

将 [后端配置模板](backend/.env.example) 复制为 `backend/.env`，将 [前端配置模板](frontend/.env.example) 复制为 `frontend/.env.local`。已有配置不要覆盖。

主要填写：

- **聊天模型**：`SUPPORT_MODEL_API_KEY`，以及对应模型名称、接口地址。
- **数据库**：确认 `SUPPORT_DATABASE_URL` 与本地 PostgreSQL 配置一致。
- **Neo4j**：设置 `SUPPORT_NEO4J_PASSWORD`；需要使用领域图谱时，将 `SUPPORT_GRAPH_ENABLED` 设为 `true`。
- **知识库问答**：填写独立 Embedding 服务的密钥、地址、模型和实际向量维度，再开启 `SUPPORT_KNOWLEDGE_ENABLED`。
- **LangSmith**：可选，配置密钥后再开启追踪。
- **前端**：`VITE_API_BASE_URL=http://127.0.0.1:8000`。

当前一键脚本会启动 PostgreSQL 和 Neo4j，因此即使暂时不启用图谱，也需要准备 Neo4j 容器密码。已有 Neo4j 数据卷不能通过修改环境变量直接更改库内密码。

### 3. 准备镜像并启动

首次使用先打开 Docker，再准备镜像：

```bash
# 首次准备可能下载镜像；启动脚本本身不会自动安装依赖或拉取镜像。
docker compose --env-file backend/.env -f docker-compose.yml -f docker-compose.graph.yml pull

# 检查配置与依赖，再启动数据库、迁移和前后端。
bash scripts/start.sh --check
bash scripts/start.sh
```

启动后访问：

| 入口 | 地址 |
| --- | --- |
| 项目首页 | http://127.0.0.1:3000/ |
| 客户登录 | http://127.0.0.1:3000/customer/login |
| 企业登录 | http://127.0.0.1:3000/staff/login |
| 后端接口文档 | http://127.0.0.1:8000/docs |
| Neo4j 管理页面 | http://127.0.0.1:7474/ |

首次体验可先在企业登录页创建企业和首个员工账号，再注册客户账号、选择该企业咨询。

保持启动终端打开；按 `Ctrl+C` 停止本次启动的前后端，数据库容器和数据卷保留。日志位于 `logs/`。本地统一使用 `127.0.0.1`，不要与 `localhost` 混用。

## 当前边界与后续方向

- 订单为模拟订单，没有真实电商对接和支付能力。
- 人工接管已经可用，目前通过轮询更新，不是 WebSocket 推送。
- 知识库支持文本、TXT 和 Markdown，尚不支持 PDF / OCR 上传处理。
- 售后条件预判目前只覆盖“无线键盘退货 / 退款申请”的特定流程，不是全品类自动审批。
- 历史工单经验不等于统一政策；已关闭工单也不代表问题已经解决。
- 领域图谱尚未参与客服回答；下一步重点是让 Agent 结合实际情况查询完整排查路径，而不是直接将可能原因当成诊断结论。
- 尚未完成生产环境的全面安全、负载和运维验证，不应直接作为生产客服系统上线。

```text

```

## 数据与密钥提醒

不要提交 `.env`、API 密钥、数据库密码或真实客户资料。前端环境变量只能存公开配置。

知识库发布会将资料发送给配置的向量服务；问答会将相关上下文发送给聊天模型。启用追踪也可能记录调用内容，演示时建议使用合成数据，并确认供应商与追踪服务的数据处理范围。
